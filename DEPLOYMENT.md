# Pagelove deployment

The selected public site is https://hire-poker-8313.onpagelove.com/ and its owner authoring endpoint is https://dav-hire-poker-8313.onpagelove.com/. Repository: https://github.com/wesley83/scrap-league.

Build with the pinned dependencies and run the checks described in `PLAY.md`. `dist/release.json` is the inventory for the current release. Older local release folders are not uploaded. The initial public repository includes the prebuilt current release for immediate local play; source changes still require a fresh build.

Run `node tools/deploy-pagelove.mjs` in a terminal. It accepts newline-terminated JSON through hidden standard input. Send `{"op":"auth","key":"<owner key>"}` to authenticate and read the destination baseline. After the authenticated result, send `{"op":"deploy"}`. Send `{"op":"quit"}` when finished. The key exists only in process memory and is sent only to the pinned HTTPS authoring endpoint. Never paste a real key into a shell command, source file, issue, or public repository.

The publisher validates local release hashes, uploads immutable release dependencies and authored HTML content, and verifies their public readback before promoting the root entry. Mutable files use ETag conditions; absent files use `If-None-Match`. A lost write response is reconciled by readback without blindly sending another write. Existing content is backed up under ignored `.local/deployment-baselines/` before replacement; no remote file deletion is performed. Keep that directory private.

Pagelove may serialize HTML and append its observed Powered by Pagelove footer. The publisher permits only that exact footer structure during public comparison, preserves it on the served page, and checks the remaining document's semantic identity, including script/style text. It then pins the complete served root HTML hash in the deployed service-worker inventory. Other asset types must match byte-for-byte. The local `dist/` inventory remains unchanged; `audit/deployment.json` records the served hashes and whether this adjustment was necessary. A root-page deployment and its worker are sequential promotions, not a platform-wide atomic transaction. If publication stops after promotion, inspect the receipt/baselines and resume against a fresh baseline; do not delete old release folders needed by installed clients.

The release includes owner Workshop publication/discovery, native track/editor routes, and shared casual Trial/Daily boards. Board resources are provisioned separately from game assets with the create-only `node tools/publish-board-resources.mjs` workflow. It refuses to replace any document unless its complete source policy matches; existing run rows are preserved. The publisher pins the two collection paths to this game, then verifies owner and public document readback. Run the exact-host positive/negative, duplicate, pagination and expiry probes before promoting a game build that enables the client. Pagelove has no supported global policy-readiness procedure; endpoint tests establish observed behavior on this host, not a guarantee about every request worker. The boards are visibly identified as forgeable community times; local progress, personal bests and ghosts do not depend on them. Owner WebDAV intentionally bypasses platform schema validation and triggers; it is trusted authoring, not a public application-validation boundary.

Both packaging and deployment call `tools/release-gate.mjs`. Local acceptance must pass before staging, staged/provider acceptance must pass before any root/native entry promotion, and live acceptance remains required before declaring the deployment verified. `audit/current-acceptance.json` must identify the exact source/output and hash its retained evidence. A blocked or incomplete row is not a waiver. Generated social posters are mandatory public dependencies even though they are excluded from the offline pack.

For a root-entry rollback, authenticate using the same hidden input, then send `{"op":"prepare-rollback","baseline":"<existing timestamp directory>"}`. Preparation verifies private backup hashes, the destination host, current ETags and all old public dependencies. Review the returned root hashes, then send `{"op":"rollback"}`. The tool rechecks all three root entries before any write, uses ETag conditions, reconciles ambiguous responses and verifies public readback. It does not delete or roll back Workshop/catalog/board documents, native routes or immutable release folders. The operation is sequential; on a partial failure preserve the receipt and inspect current state. The local rollback fixture is not a claim that production rollback has been performed.

The handbook follow-up adds bounded preservation probes. `tools/check-release-data.mjs` seeds one owned public score and `tools/check-workshop-publication.mjs` exercises one owned circuit, catalog conflict and lost-response recovery. Both accept hidden JSON `seed` and `verify-clean` operations with an owner key. Run `seed` before publication and `verify-clean` afterward; inspect the receipts and never overwrite an unfinished fixture receipt. Cleanup uses fresh conditional writes and touches only the recorded owned identifiers. Existing score/catalog records are represented by hashes in the audit, not copied payloads. `tools/check-live-outbox.mjs` separately drops one actual accepted public response and verifies two production queue clients reconcile a single score before conditional cleanup. These helpers are repository verification tools, excluded from the shipped game.
