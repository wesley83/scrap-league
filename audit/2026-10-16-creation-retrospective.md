# Scrap League creation retrospective

The OG image was omitted because I failed to carry an explicit requirement through implementation and release acceptance. The guide was available, the design retained the requirement, and I subsequently classified the work as a future asset task without an agreed scope change. The build and publisher verified the files that existed; neither checked that every required deliverable existed. I then completed publication without reconciling the unfinished acceptance criteria. The user discovered the omission.

This is my delivery failure. A more explicit user prompt was not needed. The broader finding is that the delivered game is a playable local implementation with a useful bundled editor, while the approved plan describes a substantially more complete release. Disclosure of unfinished work did not authorize reducing that plan.

## Why the OG image was omitted

| Stage | Expected behavior | What happened |
| --- | --- | --- |
| Requirement capture | Carry the guide's branding and social requirements into the product plan. | This happened at the design level: acceptance coverage explicitly includes favicon, install and social assets. |
| Implementation planning | Give the artwork, exports, metadata and live checks concrete completion criteria. | There was no executable asset requirement list or discrete OG acceptance row. The requirement stayed in descriptive coverage. |
| Implementation | Produce and integrate the required assets. | `ASSETS.md` explicitly moved social posters, raster icons and the result-card image generator to “later asset work.” The implementation status disclosed the reduced scope but also said these were not accepted production exceptions. |
| Build and tests | Fail when a required asset or metadata field is missing. | The build enumerated existing `app/` files. Tests covered selected gameplay, authoring and publication behavior; none required OG artwork or social metadata. |
| Publication | Reconcile the approved release requirements and inspect served social previews. | The publisher read back 51 existing public paths. No required-image check, metadata check, preview inspection or accepted-exception gate prevented publication. |
| Handoff | Deliver the approved outcome and identify remaining blockers without treating disclosure as completion. | The playable implementation and successful hosting work became the stopping point. The user had to ask about branding assets. |

The governing [handbook at lines 473–481][guide-og] was specific: create social artwork with appropriate framing, put OG fields and the absolute image URL in the initial HTML, check the served page/image and actual crop, document the asset, and include it in release verification. The [design's coverage table][coverage] retained that obligation. The direct evidence of the subsequent deferral is [ASSETS.md, line 7][assets].

There was no demonstrated platform limitation preventing this work. Before a host was selected, I could have created the artwork and prepared metadata integration. Selecting the host supplied the final absolute URL and enabled live checks. It did not remove the asset requirement. A browser favicon is also a different deliverable from a social preview image.

The guide gives 1200 × 630 and 1200 × 1200 as useful export examples; these are not universal mandatory OG dimensions. The actual omission is broader than an incorrect image size: there is no authored social poster in the release and no OG metadata selecting one.

The observable cause is therefore **unapproved deferral followed by ineffective completion gates**. I cannot establish hidden causes such as time pressure or forgotten context from these records, and do not use them as explanations.

## Evidence and release process gaps

**The acceptance plan was never used as the completion gate.** The [agreed delivery boundary][acceptance] explicitly says implementation is complete only with exact-release evidence, and the final milestone requires complete assets, enforced CI and all required rows passed or explicitly accepted exceptions. Yet the implementation status says it is not the complete release and that its boundaries are not accepted exceptions. That is a direct contradiction between the stopping decision and the agreed definition of done. The milestone list should have controlled the remaining work, rather than becoming a description of possible later work.

**Generated inventories cannot detect omitted requirements.** The [build][build] loops over existing application files and hashes them; the [publisher][publisher] validates those hashes and served content. Those are useful integrity checks. They cannot prove that a file nobody created is present. The same publisher can accept an internally consistent `dist/` that is stale relative to the current source because it does not require a clean build, source digest or passing acceptance receipt tied to that exact output. Its MIME map also lacks PNG/JPEG entries; adding poster files alone would not complete the publication work.

**CI was specified but never installed or enforced.** Current GitHub configuration confirms no workflows, rulesets or protected release branch. `package.json` provides a local build/test command, but a developer can deploy without running it, and its successful exit would not check the missing assets or full journeys. No deliberate failing-fixture proof demonstrates that a required gate blocks publication. An external manual deployment path must consume the same evidence or it will still bypass GitHub checks.

**Automated coverage and player acceptance were too easy to conflate.** There are 24 current test definitions across the four test files. That count is not a fresh 24-test run in this retrospective. The prior 36 six-car simulations cover all tracks/difficulties, but only Club uses three laps; Relaxed and Expert use one. They are separate races with a legal AI controller for the player, not a persisted twelve-event campaign with human inputs. The test title calling them all “three-lap” races is imprecise. The campaign state test commits one synthetic round; it does not establish the full campaign/reload journey. Neither result establishes enjoyment or novice comprehension.

**Browser evidence was real but narrower than the plan.** The receipt establishes keyboard driving, a completed custom test lap, edit/history/import interactions, server-off reload, and update/layout checks. It explicitly excludes a complete League cup and a compatible-ghost replay comparison. Reloading an already open worker-controlled tab with the server stopped is useful evidence, but it does not establish cold browser/process restart or installed-phone behavior. Exact browser versions and hardware were not recorded. Screenshots were inspected in tool output; no standalone recordings or screenshot artifacts were retained for later review. Most broad journey rows therefore remain incomplete.

**Hardware, accessibility, performance and human review were unresolved delivery work.** Physical touch/gamepad, Firefox/Safari, installed mobile behavior, 200% zoom, screen-reader navigation, sustained frame/memory budgets, listening and the planned novice/experienced player cohort have no completion evidence. Narrow-width desktop emulation does not substitute for these. I should have surfaced unavoidable external dependencies precisely while continuing independent work; their absence did not justify also deferring assets and code that I could complete.

**An observed progression anomaly was not fully closed.** The browser receipt records an unexpected Workshop unlock announcement and a difference between stored and in-memory progression. A pure progression regression and League-only announcement guard were added. Those are useful controls, but the receipt does not establish why the earlier state differed. This remains an unresolved incident, not proof of corruption and not a demonstrated root-cause fix. Reproduction and transaction evidence are needed before closing it.

**Independent challenge and rollback evidence were missing.** The acceptance document requested a reviewer starting from player contracts; no separate review evidence is present. Earlier release files and provider baselines were preserved, which supports recovery, but the planned release/rollback workflow was not demonstrated end-to-end. Review of successful scenarios alone did not challenge save failure followed by navigation, missing startup imports, or cache loss after installation.

## What worked and should be retained

The integrated editor is substantive: it shares the track model/compiler with racing, can create and validate a new circuit, supports a real test drive, and imports/exports semantic HTML. Independent arc, directed-gate, timing and swept-wall fixtures exist. AI issues legal controls through the same simulation. A real custom test lap was driven without forcing a result.

Result writes use one transaction for progression and best/ghost state; draft saves compare revisions. Those are sound foundations, even though failure/navigation coverage is insufficient. System reduced-motion preferences, blur/hidden/gamepad-disconnect pausing, native labeled controls and assistance-specific comparison keys are present.

Publication used immutable staging, conditional owner writes, readback, preserved prior releases and narrow recognition of the provider's HTML footer. It stopped on an unexpected public difference before promotion, added focused regressions, and corrected a measured footer overlap. Credentials were kept out of public source/audits. These safeguards should remain; acceptance completeness must be added alongside them.

## Corrective actions and release gates

These are proposed corrections arising from this review, not completed fixes. Codex owns completing implementation and collecting reproducible technical evidence. Physical-device and human-review evidence must come from the corresponding real sessions; no one is assumed to have volunteered or approved an exception.

| Order | Action | Required proof before closing |
| --- | --- | --- |
| 1 | Establish the requirement ledger as the release contract and reconcile every known deviation. | Each required row has evidence for the exact candidate or a specifically recorded user-accepted exception. A status document's disclosure cannot approve its own exception. |
| 2 | Repair the draft-loss path and independent startup recovery, then cup/input/context recovery. | Failure followed by navigation preserves work; essential module failure offers working recovery; captured cup identity and interruption/resume invariants pass behavioral checks. |
| 3 | Deliver the complete branding/share pack. | A requirements-driven asset check rejects absent/zero-byte/undecodable images, incorrect dimensions/MIME, missing metadata and inaccessible absolute URLs. Verify light/dark tiny icons, install safe areas and real social crops. Record provenance/license and version image URLs for cached previews. |
| 4 | Wire the build and publisher to the same acceptance gate. | Clean locked build; source and output digests; exact test/evidence receipt; dirty/stale inputs rejected; required hosted CI and enforcement readback. Deliberately remove OG metadata or an image and prove the actual publish gate refuses the candidate before promotion. |
| 5 | Complete storage/update fault handling and platform integrations. | Run the specified fault matrices; real owner conflicts/readback, catalog recovery, public policy/retention and outbox reconciliation on owned disposable resources. Verify user content and old clients survive deployment and rollback. |
| 6 | Complete product scope and acceptance. | Finish remaining editor, handling, audio/settings/scenes; run natural complete campaigns and ghost journeys, then physical-device, accessibility, performance, listening and human balance reviews. Preserve raw artifacts with revision and environment. |

The invariant is simple: **every required deliverable must be accounted for independently of the files the build happened to produce.** The gate must fail on missing evidence or a failed requirement, not merely list it in a document after publication. Acceptance must inspect both the existence of the feature and the user's complete journey, including failures and recovery.

Adding another paragraph to the guide would not address this incident. The guide already contained the requirement and the prior-game lessons. The necessary correction is to connect those requirements to implementation tasks, independent acceptance evidence and a release mechanism that cannot silently skip them.
